## 服务数量与合并结论

线上看到的 5 个 systemd 单元并不等于 5 个 VControlHub 核心服务：

| 单元 | 所有权 | 职责 | 是否合并 |
| --- | --- | --- | --- |
| `vcontrolhub-next` | 项目 | HTTP、页面、API、通知 WebSocket | 保持独立 |
| `vcontrolhub-worker` | 项目 | 定时任务、队列领取、租约与重试 | 保持独立 |
| `vcontrolhub-ssh-ws` | 项目 | 长连接 SSH 终端代理 | 保持独立 |
| `caddy` | 基础设施 | TLS 证书和反向代理 | 不是项目进程；约 10 MiB，无合并收益 |
| `postgresql` | 基础设施 | 持久数据、任务队列和审计记录 | 不是项目进程；不能并入 Node 进程 |

代码的 Next instrumentation 支持在开发环境把 Worker 跑在 Web 进程中，因此技术上可将
3 个项目进程缩为 2 个。但生产环境不启用这种拓扑，原因如下：

- Web 发布或崩溃会同时中断定时任务、审批后执行、备份和恢复；独立 Worker 可继续运行。
- 后台命令、批量 SSH 和 AI 调用的 CPU、内存及事件循环压力不应拖慢登录和管理页面。
- SSH 终端是长连接和高权限边界；独立进程具有更窄的 systemd 文件权限与资源上限，崩溃时不带走 Web。
- 当前主机总内存约 11 GiB、可用约 9.9 GiB，不存在需要用故障隔离换取约 200--260 MiB
  Worker 常驻内存的压力。

结论：此前“5 个核心服务”的表述不准确，应称为“3 个项目进程 + 2 个基础设施依赖”。
当前不合并生产进程。只有在小于 2 GiB、无关键定时任务的单机体验环境中，才值得另行设计、
测试和支持紧凑部署档；不能直接停用 Worker 单元了事。

## 清单裁决

| 编号 | 当前结论 | 处理 |
| --- | --- | --- |
| F-01 SSH 终端自动重连 | 不修改 | WebSocket 重连会创建新 shell，不能恢复 cwd、环境变量、前台程序或未保存状态。界面已有明确的手动“重新连接”。只有引入持久 session id/tmux 恢复后，自动恢复才不误导用户。 |
| W-05 恢复任务 `take: 1000` | 不修改 | 每轮分别最多处理 1000 个可重试和 1000 个耗尽任务，处理后不再匹配；15 分钟后继续，领取路径也会内联回收。该上限是数据库负载保护，不会永久遗漏。若监控证明积压增长快于恢复速度，再改为有总批次/总耗时上限的分页，不能无界清空。 |
| W-06 依赖恢复错误标记反查 | 不修改 | 在条件更新只成功一部分时，`status + errorMessage` 用于确认是本次恢复写入，而不是并发路径碰巧改成 `PENDING/FAILED`。仅按 id/status 反查会错误归因。未来可用 recovery batch id 替代文本标记。 |
| S-14 ITSM 入队失败只记日志 | 不修改 | fan-out 是不阻断工单主事务的 best-effort 边界；入队失败通常意味着同一数据库不可写，在该 catch 中再写数据库通知并不可靠，且此层没有确定接收人。应在具备独立告警通道和明确值班接收策略后实施。 |
| S-20 成本同步写回 `teamId` | 不修改 | 自动成本记录的归属来自源服务器，系统没有成本记录跨团队转移接口。同步时跟随服务器归属可防止迁移服务器后留下跨团队成本孤儿。 |
| S-21 币种可能为空 | 不修改 | Prisma 中 `Server.costCurrency` 和 `CostEntry.currency` 都是非空 `String` 且默认 `CNY`；当前类型和数据库约束均不允许该分支。 |
| S-18 客户端透传 `details` | 不修改 | `details` 是标准错误协议的一部分，表单用它呈现字段级校验。客户端删除并不能形成安全边界，因为原始 body 仍在；服务端 `apiCatch` 只为显式 `AppError` 输出 details，普通 5xx 不透传异常文本。发现具体路由泄密时应修路由。 |
| W-01 短任务只有一次心跳 | 修改 | 审查方向正确。服务器数量、计划数量和外部 API 延迟会使“短任务”超过经验租约。SLA、告警、健康采样、成本快照、历史清理、AI 运维扫描、备份调度和 ITSM 投递现已用 `runWithLeaseHeartbeat` 包住实际执行段，并保留首次即时心跳。流量采样已在上一提交完成。 |
| W-03 手工 `KNOWN_JOB_TYPES` | 不修改 | 运行时不能从 Worker registry 反向导入该集合，否则形成已记录的循环依赖。现有测试扫描源码中全部 `_JOB_TYPE` 常量并要求都在集合中，曾实际捕获 quick-service 拼写漂移；CI 失败比仅记录 runtime warning 更可靠。 |
| I-02 内部英文 `Error` | 不做批量修改 | 大部分是队列协议、配置、上游响应和日志诊断，普通 5xx 已被 `apiCatch` 隐藏。机械翻译会破坏稳定日志检索。只对确认直接到达用户界面的具体调用链做本地化。 |
| P-1 同步更新竞态返回 P2025/500 | 修改 | 另一份审查正确。已改为带原始 `teamId` 的原子 `updateMany`，`count=0` 时抛 `NotFoundError`，成功后按同一归属重新读取；避免罕见竞态变成不一致的 500。 |
| P-2 SSE 无手写重连上限 | 不修改 | 原生 `EventSource` 已持续重连，页面另有轮询降级。额外次数上限会使长时间断网后永久停止自动恢复。 |
| P-3 内部英文错误 | 不修改 | 与 I-02 相同；保持内部错误稳定，仅修明确的用户展示边界。 |
