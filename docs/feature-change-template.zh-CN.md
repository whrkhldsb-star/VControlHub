# VControlHub 功能变更说明模板

用途：先明确希望用户得到什么行为，再据此修改实现、检查既有功能并记录发布结果。关联的当前功能和编号见[项目指南第 1 章](project-overview-and-user-guide.zh-CN.md#functional-goals)，维护流程见[第 24.9 节](project-overview-and-user-guide.zh-CN.md#feature-upgrades)。

使用时复制本文件，替换下列占位内容。可将具体变更保存为 `docs/changes/CR-YYYYMMDD-NNN-简短名称.md`；该目录可在第一份变更落地时创建。一份变更可以引用多个功能编号。小改动可精简条目，但应保留当前行为、目标行为、验收条件、兼容影响和验证结果。

本文件是空白模板，不代表已经决定或实施任何新增功能。设计草稿中的示例参数不应直接当成生产配置。

## 变更信息

| 字段 | 填写内容 |
| --- | --- |
| 变更编号 | `CR-YYYYMMDD-NNN` |
| 标题 | 用一句话描述用户能感受到的变化 |
| 关联功能 | 例如 `F-07` 浏览器 SSH；引用指南中的固定功能编号 |
| 需求状态 | 草稿／已确定／开发中／待验收／已发布／已撤回 |
| 当前代码基准 | 分支及完整提交号 |
| 当前文档位置 | 章节、功能编号及相关说明链接 |
| 目标版本 | 版本号或待安排；没有排期时明确写“待安排” |
| 负责人及更新日期 | 填写维护者和最后修改日期 |
| 发布状态 | 尚未部署／验证环境已部署／指定实例已部署，并记录对应提交 |

“开发完成”“合并代码”“已经在用户实例生效”是不同状态，不能互相替代。

## 一、用户问题与功能目标

- 谁使用：账号角色、团队身份及相关资源权限。
- 在什么场景使用：从哪个页面或接口进入，用户要完成什么事情。
- 当前困难：具体输入、现有结果及造成的影响。
- 目标收益：希望减少哪些步骤、支持哪些新场景或修正什么行为。
- 不改变的部分：本次明确不处理、需保持原样的相关行为。

## 二、当前行为与目标行为

用“现在怎样 → 希望怎样”逐条对照。当前行为应能在当前代码基准中找到依据；目标行为写用户能观察到的结果，不写实现方式。

| 场景 | 当前行为 | 目标行为 | 依据（页面、接口或源码位置） |
| --- | --- | --- | --- |
| 主要成功路径 | 现有输入、操作和结果 | 变更后应得到的结果 | 指南章节、源码链接 |
| 拒绝或无权限 | 当前提示及状态 | 应如何拒绝、提示什么 | |
| 失败或中断 | 当前错误、重试和遗留状态 | 应保留什么、如何恢复 | |

如果暂时无法确认当前行为，写明“待核实”及核实方法，不要按推测填写。

## 三、范围与兼容要求

- 本次包含：页面、接口、后台任务或部署配置中需要变化的部分。
- 本次不包含：相关但留待以后处理的事项，以及原因。
- 必须保留的旧行为：其他入口、已有数据、已保存的配置、API 调用方和脚本继续按原约定工作。
- 权限与团队边界：哪些角色、权限或工作区范围受影响；拒绝时不应泄露资源是否存在。
- 数据与配置兼容：是否新增字段、迁移、环境变量或设置项；旧版本代码能否继续读取新数据；默认值是什么。
- 界面与语言：中英文文案、深浅主题、窄屏布局和无障碍要求。

## 四、验收条件

每条条件都应能由他人独立执行并得出“通过／不通过”。至少覆盖成功、拒绝、失败和兼容四类场景。

| 编号 | 场景 | 前置条件 | 操作 | 预期结果 |
| --- | --- | --- | --- | --- |
| AC-1 | 成功 | 账号角色、资源状态、配置 | 具体步骤或请求 | 可观察结果：页面、返回值、记录或文件 |
| AC-2 | 拒绝 | 缺少的权限或不允许的状态 | 同上 | 拒绝方式、提示内容，且未产生副作用 |
| AC-3 | 失败 | 外部依赖不可用、超时或中途取消 | 同上 | 状态如何呈现，能否重试，数据是否一致 |
| AC-4 | 兼容 | 升级前已存在的数据或调用方式 | 同上 | 原有行为不变 |

状态描述应区分已提交、已批准、执行中、已完成、已取消和结果未知；“请求已受理”不等于“操作已经完成”。

## 五、影响分析

沿指南的源码索引逐项核对，没有影响的写“无”，不要留空：

- 页面与组件：
- 接口与 Server Action：
- 权限、团队与资源授权：
- 数据模型与迁移：
- 后台任务、Worker 与实时通道：
- 外部依赖与部署配置：
- 文档：本指南章节、README、API 文档及 HTML 阅读版。

一个界面开关可能对应多个调用入口，应按真实调用关系分析，而不是只看触发它的页面。

## 六、实现与验证记录

| 项目 | 记录 |
| --- | --- |
| 实现分支／PR | 分支名、PR 链接 |
| 相关提交 | 完整提交号及说明 |
| 新增或修改的测试 | 测试文件与覆盖的验收编号 |
| 执行的检查 | 类型检查、lint、单元／集成测试、文档检查及结果 |
| 回归范围 | 按影响分析选择的既有功能及验证结果 |
| 未完成事项 | 尚未满足的条件、已知限制及后续安排 |

逐条报告验收编号的结果。实现中发现需求矛盾或额外影响时，先回到本文补充说明，再按明确后的需求处理；不能降低原定的验收标准。

## 七、发布与文档回填

- 发布前：数据备份方式、迁移是否兼容旧代码、需要提前设置的配置。
- 发布：部署的实例、版本或提交、时间及操作人。
- 发布后验证：实际执行的链路检查及结果，例如登录、原有 SSH、文件读写和后台任务。
- 回退方案：出现问题时如何恢复程序和数据；数据库迁移是否可逆。
- 文档回填：已兑现的行为写入指南正文，更新基准提交、功能清单、数量统计和 HTML 阅读版；未完成部分继续标注状态和限制。
