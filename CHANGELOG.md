- **Sync can log in to its target with a one-time key instead of the target's own credential (opt-in).** The source runs the transfer's ssh client, and it receives the target server's own private key, or its password as `SSHPASS`, in `/tmp` for the whole run (up to 12 h), where root on the source can copy it. That stays the default ("Original"). Each server now has a sync login choice in its create and edit form: follow the platform setting, Original, or One-time key; the platform setting is `sync.targetAuthDefault` (Settings → Login and connection policy, default Original). Migration `20261105040000_server_sync_target_auth` adds `servers.syncTargetAuth` and sets every existing server to Original, so changing the platform setting never changes how they are synced; servers added later follow it until given their own choice. Each leg of a job goes by the server it writes to, and the choice travels with configuration export and import. With a one-time key, each run (each direction of a bidirectional job) gets an ed25519 key made on the hub. Over its own SSH connection the hub adds the public half to the target user's `~/.ssh/authorized_keys`, pinned to a forced command that allows only `rsync --server` as a receiver into the job's target directory (each option checked against what the job sends, `--delete` only for deleting jobs, no `--sender`, no `--protect-args`; the destination is the job's whatever the source names) or the tar fallback's three fixed steps, with `restrict`, an `expiry-time` (run limit plus one hour) and `from=` the address the source connects from. Only the private half goes to the source. The line is removed when the run ends, whatever the outcome; a run that died has its lines and key files removed on both servers by the stale-RUNNING reclaim, the next install on that host removes them too, and they stop working at their expiry time anyway. Such a target must allow public-key login for the sync user through `~/.ssh/authorized_keys` (`restrict` from OpenSSH 7.2 and `expiry-time` from 7.7 are used when its `ssh -V` reports them, older versions get the `no-*` options), and the hub's session to it must be that user; a target that refuses the key fails with an error that says so and how to switch the server back to Original, never by falling back to its password.
- **Review follow-ups (2026-11-05), behaviour changes.** A customer's direct-download link is signed only with its server's own gateway key: a node without a server, or on a gateway that still holds the shared secret, is served through the hub for everyone but the platform administrator (enable such a gateway again to move it to its own key). Changing a server's address, port or user name needs its password again (Linux SSH, Windows RDP and SFTP); the stored password is never sent to a new endpoint. Editing a sync job needs reach to both of its servers, and whoever changes what, where or when it copies becomes its creator, so scheduled runs act with the editor's rights. Resuming, pausing or rescheduling a scheduled task that runs without per-run approval needs `command:execute`, as the toggle does; whoever rewrites a task's command must reach its servers and files its later runs. Changing a playbook's trigger, enabled state or retries needs `playbook:run` (and `command:execute` for command steps); only a platform administrator takes over a playbook whose owner is still active. The email and Telegram alert channels, which deliver to the platform's own recipients, are for platform administrators, and a customer's incident list no longer shows the platform's delivery errors or on-call users. A read permission granted through an API token never authorises a POST, PUT, PATCH or DELETE. Deleting every alert rule no longer brings the starter rules back (settings `alerts.defaultRulesSeeded`, per customer `alerts.defaultRulesSeeded:<id>`).
- **Review follow-ups (2026-10-29), behaviour changes.** Each managed server's direct-download gateway now verifies links with a key derived for that server (`HMAC(secret, server id)`) instead of the hub's shared secret, which root on any one managed server could use to sign links for every other; gateways installed earlier keep the shared secret (`servers.directGatewayKeyVersion = 1`, migration `20261029050000_direct_gateway_key_version`) until the gateway is enabled again. Sync jobs: a caller without `server:ssh` may only name paths inside the server's storage root (a server without a storage node needs `server:ssh`). The traffic pages show the hub host's own interfaces to platform administrators only. Cloud billing accounts return their CSV sample and feed URL to `cost:manage` holders only. Binding a playbook to an alert rule needs `playbook:run`. AI: plan-only mode is enforced where tools run, not only in the list shown to the model; the unattended read tools (`read_file`, `list_files`, `search_files`) refuse password and key files, credential stores, `.env` files, shell histories and device nodes; a provider key that cannot be decrypted is reported instead of sent as ciphertext. Magnet links: trackers on private, loopback or local addresses, with credentials, or over non-tracker schemes are dropped before aria2 announces to them.
- **Remote desktop on phones and tablets follows Microsoft's Remote Desktop app.** The pointer modes are named and behave as its "Mouse pointer" and "Direct touch" do. Mouse pointer: a drag moves the pointer, a tap is a left click, a two-finger tap a right click, a tap followed at once by a press-and-drag (or a half-second press) holds the left button, two fingers up or down are the mouse wheel, a pinch zooms (up to 5×) and a pan knob moves the zoomed picture; the pointer pushed against the picture's edge carries the picture along. Direct touch: a tap clicks under the finger, tap-and-hold then release (a ring grows and the phone buzzes) is a right click, a drag holds the left button from where it began; two fingers still scroll and zoom. Above the on-screen keyboard there is a row of extra keys (Esc, Tab, Ctrl, Alt, Shift, Win, arrows with key repeat, Home, End, PgUp, PgDn, Del, F1–F12); Ctrl, Alt, Shift and Win are armed for the next key or click, locked by a second tap, and released with the keyboard. While the keyboard is up the remote desktop keeps its size instead of being resized to the half of the panel that is left. Resolution switching, Ctrl+Alt+Del and full screen are unchanged. The gesture recogniser, the view geometry, the sticky modifiers and the keyboard controller are plain modules under `src/lib/rdp/` and `src/components/rdp-*` with fake-clock unit tests.
- **Full review round (2026-10-28), behaviour changes.** Customer accounts can no longer register a server at a hub-local address (127.0.0.1, localhost, ::1, 0.0.0.0), which made a storage node rooted at any hub directory; an authenticator code is single use; setting up two-factor authentication asks for the current password (`npm run admin:reset-2fa -- <username>` clears a lost second factor); passwords are 8–128 characters everywhere; the account lockout key is normalised and bounded; a `.env.runtime` no longer keeps a stale `DATABASE_URL` (other kept secrets warn when `.env.local` differs).
- Changing the command or target servers of a scheduled task that runs without per-run approval needs `command:approve`, and retrying one needs `command:execute`; a request an approver approved runs on that approval even when its requester only holds `command:create`.
- MOVE with `Overwrite: T` onto a folder needs the delete permission; uploads onto a folder are refused (409); file names are limited to 255 bytes, not 255 UTF-16 units; compress, extract and archive listing respect the recycle bin.
- The process-wide aria2 speed limit and totals are for platform administrators; three downloads run at once instead of one; direct downloads honour their speed limit; `/status` shows the platform-wide component checks to platform administrators only; transfer rates are shown as KB/s, MB/s, GB/s.
- Migration `20261028150000_file_preferences_entry_index` (expand-only): an index on `file_preferences.fileEntryId` (deleting 2,000 file entries took ~16 s without it).

- The health sampler and Agent metric reports also write one normalised row per server (`server_metric_latest`): rates in bytes per second from interface counters (unknown after a counter reset, an interface change or a gap longer than three report intervals; never zero by default), monthly traffic by deltas, the latest reachability verdict and TCP probe. Each `metric_snapshots` row now records the sampler interval and the probe outcome (`ok`, `failed`, or not measured when a fresh Agent report was used).
- **Daily uptime counts covered minutes from real sample times.** Each sample covers the time until the next one, at most twice its recorded interval (rows written before the interval was recorded: the former fixed 5 minutes), and the day's percentage is the online share of that covered time. A changed sampling interval no longer rescales history or makes complete days look "insufficient"; the `/status` heatmap's coverage is judged in minutes.
- A published node disappears from every public view as soon as it is unpublished, its server is disabled, the server moves to another customer (the board recorded the owner at publish time; republishing confirms the new owner) or its customer is deleted — the cached board list re-checks the visible set on every request, so this holds without waiting for the cache.
- Anonymous `/` gets a real `307` (to `/status` when the board is open, otherwise `/login?next=/`) and a hidden, unpublished or unknown `/status/nodes/<id>` a real `404`: the proxy decides these two entry points with one indexed query before the page streams (the root loading screen otherwise forces a streamed `200`).
- Metrics read from an Agent report carry the report's own time instead of the time the sampler parsed them; server traffic history uses the first physical interface instead of whichever interface `/proc/net/dev` lists first (often `docker0`).
- `/status` for signed-in accounts shows the public board first and the internal component checks and customer uptime below it; with the board closed, visitors see the overall status only, as before.

### Fixed

- **Content search on remote nodes skipped files the local search found (2026-11-13).** The remote command carried its own list of 43 extensions, which had drifted from the local one: files without an extension (Dockerfile, Makefile, README, `.env`, `.gitignore`) and a few extensions (`.gradle`, `.dockerfile`) were searched on LOCAL nodes only. The remote `--include` list is now generated from the local one; a test searches the same files both ways and expects the same answer.
- **Tests after the Windows CI fixes (2026-11-13).** The host-key test retried ssh2's ed25519 generator in a loop of its own; it uses the existing `generateEd25519KeyPair` helper, as does the SSH key crypto test, which called the generator directly and failed about once in 256 runs. The backup schedule integration test restored every paused schedule of other servers when it finished, including ones paused on purpose; it restores the ones it paused. The 7z listing test checks every directory again except on Windows.
- **Linux Agent: a stop that arrived while a command was being started left the command running, unreported (2026-11-12).** `SIGTERM` (a service stop or restart) is turned into an exception so that a running command is ended and its result handed in. Raised between starting the command and beginning to watch it, the exception left `run()` with the command still running and no result: the Agent exited without a word, nobody ended the command, and the hub waited out its lease and recorded an unknown outcome. A unit test failing now and then under load showed it; sending the stop at growing delays (0–3 ms) after the hub hands a job out reproduces it every time. A stop in that window, or while the result is being put together, is now noted and acted on at the next check: the command is ended and reported (exit code 143), then the Agent leaves. `AGENT_VERSION` is unchanged, so installed Agents keep their build until the version is raised (which makes running Agents update themselves) or they are installed again; the Windows Agent was not examined for this.
- **Alert rules: a rule with a webhook could not be edited, and every API answer carried the webhook address (2026-11-12).** The stored address is never sent to the page, so the edit form submits the channels without it; the update schema refused any change that named the webhook channel without an address, so changing a threshold or a cooldown on such a rule failed unless the address was typed again, and nothing on the form said so. The requirement is now checked against the rule (the address in the change, or the one already stored), and the form says that an empty field keeps the stored address. Separately, `GET`, `POST` and `PATCH /api/alert-rules` answered with the database row: the address (which usually carries a token) was in every answer, and the row has no `webhookConfigured`, so the page's "webhook configured" badge disappeared after its first refresh. The page and the API now share one shape (`src/lib/alert/rule-dto.ts`), which says whether a webhook is configured and never carries the address.

- Account lockout can no longer be used to lock someone else out. Failed logins used to count per username alone, so anyone who knew a username could lock its owner out for 15 minutes with five wrong guesses. Failures now count per username **and** source address (five misses lock that address), with a separate account-wide ceiling of 25 misses across all addresses that locks the account for everyone and is recorded in the audit log with its scope; a successful login clears both.

- Login no longer stalls the whole server. Password hashes were checked with `bcryptjs`, which runs the bcrypt rounds in JavaScript on the event loop: at cost 12 one check held every request for about 350 ms, and a dozen concurrent logins (a team signing back in after an outage, or a credential-stuffing attempt from several addresses) froze pages and APIs for several seconds. Hashing now uses the native `bcrypt` module on the thread pool; stored hashes are unchanged and keep verifying. The module ships prebuilt binaries for Linux (glibc and musl), macOS and Windows, so no compiler is needed on install.
- Share-link password throttling now works per client and per share. The limiter key was built by smuggling `ip:share:token` through a forged `x-forwarded-for` header, and the 48-character token pushed that value past the client-IP normaliser's 64-character cap, so every guess for a share fell into one shared bucket: eight wrong guesses from anyone locked a password-protected share for everybody for 15 minutes. The key is now derived directly from the share token and the caller's address.
- Sync jobs keep a hostile target path out of the target host's shell. rsync hands `user@host:path` to the remote login shell, and versions older than 3.2.4 (Debian 11, Ubuntu 20.04) do not escape it, so a `targetPath` containing `;` or `$(...)` ran as the sync user on the target VPS with only `storage:write`. rsync now runs with `--protect-args`, and sync endpoint paths reject control characters at the API.
